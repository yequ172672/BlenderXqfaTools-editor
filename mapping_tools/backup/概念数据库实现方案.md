# 骨骼概念表自动映射方案

## 目标

为自动映射提供**骨骼功能分类参考表**：将不同命名体系中的同一根功能骨骼归为一组。例如 "head"、"Head"、"Bip01-Head"、"mixamorig:Head" 都指向"头部"这根功能骨骼。

该表从用户已有预设数据自动派生，用户保存新预设后自动去重合并——**无需手动维护**。

## 核心数据结构

### 骨骼概念表（Bone Concept Table）

从所有预设自动构建。每个概念条目以**目标骨骼名**（即预设中 `.bone` 字段的值）为键，所有曾映射到该目标骨骼名的源名（`.vg` 字段值）为别名集合：

```python
# 内存结构
_concept_table = None   # Dict[str, set]  → {concept_id: {alias1, alias2, ...}}
_name_lookup = None      # Dict[str, str]  → {name_lower: concept_id}  用于 O(1) 查询
```

构建示例（从预设数据自动生成）：

```
"head"        → {"head", "bip001-head", "def-head", "mixamorig:head", "b005:head", ...}
"neck"         → {"neck", "bip001-neck", "def-neck", "neck_01", "mixamorig:neck", ...}
"upperarm_l"   → {"upperarm_l", "l_upperarm", "leftarm", "bip001-l-upperarm", "mixamorig:leftarm", ...}
"upperarm_r"   → {"upperarm_r", "r_upperarm", "rightarm", "bip001-r-upperarm", "mixamorig:rightarm", ...}
"spine_01"     → {"spine_01", "spine", "bip001-spine", "def-spine", "mixamorig:spine", "spine1", ...}
"spine_02"     → {"spine_02", "spine1", "bip001-spine1", "chest", "def-spine.001", "spine2", ...}
...
```

实际数据量：现有 63 个预设 → ~1668 个唯一骨骼名 → 约 120-150 个有意义的独立概念条目（去重后，核心骨骼约 52 根左右符合重定向需求，其余为服饰/头发/辅助骨骼概念）。

### 构建流程

```python
def _build_concept_table(pair_counts):
    """
    从预设 pair_counts 构建概念表。
    pair_counts: {(vg_lower, bone_lower): count}
    
    规则：
    1. bone_name 作为 concept_id
    2. 所有映射到同一 bone_name 的 vg_name 都是该概念的别名
    3. bone_name 本身也是别名（自引用）
    4. 一个名字同时出现在多个概念时，选择出现次数最多的归属
    """
    concepts = {}    # concept_id -> set of aliases
    name_freq = {}   # name_lower -> (best_concept_id, frequency)
    
    for (vg, bone), count in pair_counts.items():
        concept_id = bone
        if concept_id not in concepts:
            concepts[concept_id] = set()
        concepts[concept_id].add(vg)
        concepts[concept_id].add(bone)  # 自引用
        
        # 记录 vg 的归属频率（解决冲突）
        if vg not in name_freq or count > name_freq[vg][1]:
            name_freq[vg] = (concept_id, count)
    
    # 构建逆索引：name → concept_id
    name_lookup = {}
    # 先写入高频归属
    for name, (concept_id, _) in name_freq.items():
        name_lookup[name] = concept_id
    # 再写入概念名自身的映射（概念名优先级最高）
    for concept_id in concepts:
        name_lookup[concept_id] = concept_id
    
    return concepts, name_lookup
```

### 冲突处理

同一骨骼名可能出现在多个概念中（不同预设把同一个名字映射到不同目标骨骼）。例如 "spine" 在某些预设映射到 "spine_01"，在另一些预设映射到 "spine"。

解决方案：**频率投票**——统计该名字在所有预设中出现时各映射目标的频次，选择频次最高的归属。极端情况（频率相同）保留首次出现的归属。

### 持久化 JSON 缓存

概念表构建完成后，缓存为 JSON 文件，避免每次重启都重新解析所有预设：

```
位置: bpy.utils.resource_path("USER")/scripts/xqfa_concept_cache.json
结构: {
    "version": 1,
    "preset_mtime": <最新预设文件的修改时间戳>,
    "concepts": { "head": ["head", "bip001-head", ...], ... }
}
```

加载时检查最新预设文件的 mtime：
- mtime 未变 → 直接读 JSON 缓存（毫秒级）
- mtime 变化 → 重新从预设构建并写入 JSON 缓存

### 与旧预设系统的关系

| | 旧预设系统 | 概念表 |
|---|---|---|
| 数据来源 | 用户手动保存的 `.py` 预设文件 | 从预设自动派生 + JSON 缓存 |
| 写入 | `add_presets` 写入 `.py` 文件 | 新预设保存后自动重建概念表 |
| 读取 | `load_preset_mappings()` 逐文件解析 | 先查 JSON 缓存，miss 则从预设重建 |
| 对外 | 预设菜单、加载、删除 → 不变 | 仅被 auto_map 调用 |

**用户保存新预设后**：`add_presets` 写入 `.py` 文件 → `_invalidate_preset_cache()` 清除缓存 → 下次 auto_map 触发重建 → 概念表自动包含新数据。与现有流程完全兼容。

## 匹配算法

### 概念匹配评分 `concept_bonus()`

```python
def concept_bonus(src_name, tgt_name, name_lookup):
    """
    基于概念表的确定性匹配评分。
    
    返回:
        1.0  — 同概念、同侧（确定性最高）
        0.8  — 同概念、一侧无侧别信息
        0.5  — 同概念、不同侧（可能是镜像映射）
        0.0  — 不同概念或未知
    """
    src_lower = src_name.lower()
    tgt_lower = tgt_name.lower()
    
    src_concept = name_lookup.get(src_lower)
    tgt_concept = name_lookup.get(tgt_lower)
    
    if src_concept is None or tgt_concept is None:
        return 0.0
    
    if src_concept != tgt_concept:
        return 0.0
    
    # 同概念 → 判定侧别一致性
    src_side = _detect_side(src_name)
    tgt_side = _detect_side(tgt_name)
    
    if src_side == tgt_side:
        return 1.0
    elif src_side is None or tgt_side is None:
        return 0.8
    else:
        return 0.5  # 反对侧（L vs R），可能是镜像映射
```

### 侧别检测 `_detect_side()`

```python
def _detect_side(name):
    """
    检测骨骼名的侧别信息。
    返回: 'L', 'R', 或 None
    """
    lower = name.lower()
    for prefix, side in [("left_", "L"), ("right_", "R"), ("l_", "L"), ("r_", "R"),
                         ("lt_", "L"), ("rt_", "R")]:
        if lower.startswith(prefix):
            return side
    for suffix, side in [("_left", "L"), ("_right", "R"), ("_l", "L"), ("_r", "R"),
                          (".left", "L"), (".right", "R"), (".l", "L"), (".r", "R")]:
        if lower.endswith(suffix):
            return side
    tokens = _tokenize(name)
    if tokens and tokens[-1] in ("l", "left", "lt"):
        return "L"
    if tokens and tokens[-1] in ("r", "right", "rt"):
        return "R"
    return None
```

### 新算法评分权重

| 评分维度 | 旧权重 | 新权重 | 说明 |
|---|---|---|---|
| 概念匹配 `concept_bonus` | — | 0.50 | 替代旧 `preset_bonus`，确定性更高 |
| 名称相似度 `name_score` | 0.30 | 0.25 | 概念命中时省略此计算 |
| 层级相似度 `hierarchy_score` | 0.15 | 0.15 | 不变 |
| 空间相似度 `spatial_score` | 0.10 | 0.10 | 不变 |
| **合计** | 1.00 | 1.00 | |

### 评分流程

```python
def auto_match_bones(src_armature_obj, tgt_armature_obj, threshold=0.25):
    src_bones = [b for b in src_armature_obj.data.bones if is_core_bone(b.name)]
    tgt_bones = [b for b in tgt_armature_obj.data.bones if is_core_bone(b.name)]
    
    # ... bbox 计算、缓存 ...
    
    algorithm = bpy.context.scene.auto_map_algorithm
    
    if algorithm == 'CONCEPT':
        concept_table, name_lookup = load_concept_table()  # JSON缓存或从预设重建
        CONCEPT_THRESHOLD = 0.7  # 概念分 >= 此值 → 确定性匹配，跳过其他评分
        
        for sb in src_bones:
            src_lower = sb.name.lower()
            src_concept = name_lookup.get(src_lower)
            for tb in tgt_bones:
                cb = concept_bonus(sb.name, tb.name, name_lookup)
                if cb >= CONCEPT_THRESHOLD:
                    # 快速路径：概念命中，直接用概念分
                    scores.append((cb, sb.name, tb.name))
                    continue
                # 慢速路径：概念未命中，回退到名称+层级+空间
                ns = name_score(sb.name, tb.name)
                hs = _cached_hierarchy_score(sb, tb)
                ss = _cached_spatial_score(sb, tb)
                total = 0.25 * ns + 0.15 * hs + 0.10 * ss
                scores.append((total, sb.name, tb.name))
    else:
        # 旧算法：完全不变
        preset_data, vg_index, bone_index = load_preset_mappings()
        max_preset_count = max(preset_data.values()) if preset_data else 0
        for sb in src_bones:
            for tb in tgt_bones:
                ns = name_score(sb.name, tb.name)
                hs = _cached_hierarchy_score(sb, tb)
                ss = _cached_spatial_score(sb, tb)
                pb = preset_bonus(sb.name, tb.name, preset_data, vg_index, bone_index, max_preset_count)
                total = 0.30 * ns + 0.15 * hs + 0.10 * ss + 0.45 * pb
                scores.append((total, sb.name, tb.name))
    
    # 后续贪心匹配不变 ...
```

## 性能优化：概念命中的早退机制

旧算法**每一对骨骼都计算全部 4 项分数**。概念表的核心优势：**命中率高的骨骼对直接跳过名称+层级+空间计算**。

| | 旧算法 | 新算法（概念表） |
|---|---|---|
| 命中概念 | 无 | 概念分 ≥ 0.7 → 直接打分，O(1) |
| 未命中概念 | 全部 4 项评分 | 3 项评分（无概念加成） |
| 常见骨骼命中率 | — | ~60%（有预设覆盖的核心骨骼） |
| 200×200 预估 | ~10s | ~4-5s（命中部分跳过名/层级计算） |

JSON 缓存加载：< 5ms（从文件读取约 50KB JSON）。
预设重建：约 50ms（扫描 63 个 .py 文件 + 构建 + 写 JSON 缓存）。

## 测试要点

1. **概念表构建正确性**：验证所有预设中的 `(vg, bone)` 对都被正确归入概念，`name_lookup` 索引的 key 覆盖与 `pair_counts` 一致
2. **冲突处理**：验证同一名字在多个概念中时，频率最高的归属胜出
3. **侧别检测**：验证 `_detect_side()` 对各种命名风格（前缀/后缀/驼峰token）的 L/R 判定
4. **新算法匹配质量**：用同一对骨架（如 MMD vs UE）对比新旧算法输出，新算法应：
   - 对有预设覆盖的骨骼给出更高、更确定的分数
   - 对无预设覆盖的骨骼回退到名称+层级+空间评分（与旧算法 preset_bonus=0 一致）
5. **性能**：新算法在有预设覆盖的场景下应明显快于旧算法
6. **旧算法回归**：选择"预设匹配"算法时，输出与修改前完全一致
7. **预设更新后自动生效**：保存新预设 → 运行 auto_map → 概念表包含新数据
